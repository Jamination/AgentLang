# std.dx12

`use std.dx12`. Direct3D 12 and DXGI bindings, generated by `tools/gen_dx12.al` from the
mingw-w64 C headers (`d3d12.h`, `dxgi*.h`, `d3dcommon.h`, `d3d12sdklayers.h`,
`d3dcompiler.h`): 211 enums, 278 structs, 124 COM interfaces with 2667 methods, 133 interface
ids and the exported entry points, plus the few user32 / kernel32 functions a program needs
to open a window.

**Status: type-check only.** `alc` emits x86-64 Linux executables. A program that uses this
module passes `alc check` (which also checks every function of the module), but
`alc build` stops with

```
error: `CreateEventW` is imported from `kernel32.dll`, which is not a Linux library; ...
```

A Windows backend needs a PE/COFF writer with an import table in place of the ELF writer, and
the Win64 calling convention for `extern` calls and for AL functions passed as callbacks
(`window_proc`): four register arguments in rcx / rdx / r8 / r9 with shadow space, and structs
larger than 8 bytes passed by reference. The bindings already describe COM methods that
return structs the way the Windows ABI passes them (hidden result pointer), so they do not
have to change.

## Mapping rules

| C | AL |
|---|----|
| `UINT`, `DWORD`, enum types, flag types | `u32` (`INT`, `LONG`, `BOOL`, `HRESULT`: `i32`) |
| `UINT64`, `SIZE_T`, `D3D12_GPU_VIRTUAL_ADDRESS` | `u64` |
| `FLOAT` | `f32` |
| `LPCSTR`, `void *` | `*u8`; `LPCWSTR`: `*u16` (see `utf16`) |
| `HANDLE`, `HWND`, `HINSTANCE` | `*u8` |
| enumerators, `#define` constants | typed constants with their C names (`D3D12_RESOURCE_STATE_PRESENT`) |
| `struct` | struct with the same fields and the Windows x64 layout |
| `union` member | a block of words plus one accessor per member returning a typed pointer (`barrier.u_Transition()`) |
| `GUID`, `IID_*` | `struct GUID` and `IID_ID3D12Device := GUID{...}` with the real values |
| interface `ID3D12Device` | `struct ID3D12Device { vt: *ID3D12DeviceVtbl }`; the vtable struct lists the methods in header order as function fields |
| method | a function with the C++ method name whose first parameter is the interface pointer: `device.CreateCommandQueue(&desc, &IID_ID3D12CommandQueue, &queue)` |
| method returning a struct | returns the struct (`heap.GetCPUDescriptorHandleForHeapStart()`); the wrapper passes the hidden result pointer |
| `void **ppv` out-parameter of a method | a pointer to your typed interface variable (`&queue`) |
| exported function | `extern "d3d12.dll" fn D3D12CreateDevice(...) -> i32` and so on |

Method names are shared by many interfaces (`Release`, `GetDesc`, `Map`); overloading on the
interface pointer picks the right one, and inherited methods are generated for every derived
interface, so `swap_chain.Release()` needs no cast. A function named `Map` does not hide the
core `Map[K, V]` type: types and functions are separate namespaces.

## Helpers

| | |
|---|---|
| `SUCCEEDED(hr)` `FAILED(hr)` | |
| `dx_check(hr, what)` | panics with `what` and the HRESULT in hexadecimal on failure |
| `ppv(&iface)` | an interface variable as the `void **` of an exported function: `D3D12CreateDevice(nil, level, &IID_ID3D12Device, ppv(&device))` |
| `com_release(&iface)` | `Release()` if not nil, then sets the variable to nil |
| `utf16(s) -> *u16` | NUL-terminated UTF-16 copy of UTF-8 text (allocates) |

## Sample

`tests/check/dx12_triangle.al` is a complete spinning-triangle program (360 lines) and the
reference for using the bindings:

1. `create_window`: `RegisterClassExW` with an AL function as the window procedure, `CreateWindowExW`.
2. `create_device`: optional debug layer, `CreateDXGIFactory2`, adapter selection with `EnumAdapters1`, `D3D12CreateDevice`, command queue.
3. `create_swap_chain`: `CreateSwapChainForHwnd`, `QueryInterface` to `IDXGISwapChain3`, render-target view heap and one view per back buffer.
4. `create_pipeline`: HLSL in a raw string compiled with `D3DCompile`, root signature with root constants, input layout, pipeline state, command allocator and list.
5. `create_vertex_buffer`: upload heap, `Map` / copy / `Unmap`, vertex buffer view (the `Vertex` struct is `vec3` + `vec4`, the same bytes the shader expects).
6. `render`: reset, root constants, resource barriers through the union accessor, clear, draw, `Present`, fence wait.
7. `destroy`: waits for the GPU and releases every object.

## Regenerating and verifying

```
./build/alc run tools/gen_dx12.al               # rewrites std/dx12.al and its test (byte-identical if nothing changed)
./build/alc run tools/gen_dx12.al -- --verify   # also writes /tmp/dx12_verify.c and prints how to compile it
```

The generator is an AL program, run from the repository root. It reads the headers from
`/usr/x86_64-w64-mingw32/include` (or `--include DIR`); `--quiet` leaves out the summary.
`std/dx12.al` is embedded in the compiler: rebuild `alc` after regenerating.

`--verify` writes a C file of static assertions (struct sizes, every field offset, the vtable
slot of every method, every constant value) and prints the command that compiles it against
the mingw-w64 headers with the mingw cross compiler (`x86_64-w64-mingw32-gcc -fsyntax-only -w
/tmp/dx12_verify.c`: no message means every assertion holds). Last run: 278 structs (1066
field offsets), 124 interfaces (2667 vtable slots) and 2993 constants verified. This is a
development-time check of the generator, not part of `alc` or of `verify.sh`.

`tests/std/dx12.al` (also generated) runs on Linux: it compares `sizeof` and field offsets of
the AL structs with the values computed from the headers and makes calls through a COM vtable
built in AL.
